Alchemy - Task Intent for Teams TLDR; Teams messages today lack machine-readable signals for task intent and importance. As a result, BizChat must infer intent from raw text for every query, which reduces satisfaction on task and triage scenarios. This spec defines two offline tags -  HasTask and IsImportant - to be stamped on messages along with Attribution and other Teams-specific interaction signals. Copilot can then filter and rank using these signals instead of guessing, improving response quality.SummaryThis spec introduces two offline message-level tags, HasTask and IsImportant, plus Attribution (who the ask is for) and select Teams interaction signals. Together, these create machine-readable intent and priority cues so Copilot can filter and rank messages directly instead of inferring intent from raw text at query time.Non-goals (Phase 0):Perfect freshness of tags (handled by Copilot at query time in Phase 0)Task completion state detection (tracked as a follow-on).Attachment/image intent extraction.P0 scope is 1:1 and group chats, not channelsSignals (stamped on messages)HasTask: The message expects an action, response, or decision from someone (explicitly or implicitly).IsImportant: The message is urgent or has high organizational/customer impact.Attribution: Who the ask is for - Explicit, Implicit, or Unassigned (broadcast/ambiguous).Teams' interaction signals: Followed, Saved, Reacted, ReminderHasTaskHasTask = TRUE when a message contains an explicit or implicit request for action, response, or decision from one or more recipients. This includes:Requests for Action: Produce a deliverable artifact or perform a verifiable operational step. Requests for Knowledge: Information, opinion, confirmation, permission, availability, or acknowledgment; no artifact neededSelf-directed / self-assigned commitments: The sender commits to doing work (e.g., “I’ll handle this”, “Let me send the draft by EOD”). Treat as HasTask=TRUE (task for sender), not merely informational.HasTask = FALSE when a message is purely informational, social, acknowledgment-only, a status update, or a completed-action report that does not solicit a new response. HasTask = FALSE when a message is:Purely informational (status, FYI, announcement)Social/phatic (greetings, GIFs)An acknowledgment resolving a prior ask ('Got it', 'LGTM')A completed-action report ('Done', 'PR merged', 'Invoice submitted')The tag itself is boolean. But understanding task categories helps build better training data and enables P1 composite tagging.Task TypeSub-classDescriptionCross-Domain ExamplesAction RequestRfAAsks recipient to It answers: “Is this task for me?” when Copilot serves results.Explicitly targetedIf a single @mention exists in the ask → attribute to that user.If multiple @mentions exist → attribute to the mentioned set and mark as multi-assignee (do not force a single owner).If @everyone/@channel/@team is used → mark as Explicit (broadcast), assignee=broadcast (do not force a single owner).Implicitly targetedIf there’s no @mention but the ask is clearly directed (e.g., “Andrew can you…”, strong reply-to pattern) → attribute to the inferred user and mark as implicit.If the assignee is unclear, infer an implicit assignee from interaction signals (implicit follow): replied/“I’ll take it”, thread initiator/driver, or being @mentioned in the discussion.Explicit follow (clicked Follow) can also imply implicit attribution when no other assignee is present.Never override explicit targeting; if multiple candidates qualify, keep as multi-assignee (implicit).Unassigned / ambiguousIf the message is broadcast or the “you/we” target is unclear → do not assign to a person; mark as unassigned/ambiguous and require clarification at query time (only when needed).Notes:“CC’d” vs explicitly addressed: Teams doesn’t have an email-style CC field; broad visibility (group chat/channel) should not be treated as targeting. Prefer explicit targeting signals (e.g., @mention, name, reply-to); if no assignee is present, implicit targetting and interaction signals (followed/replied/initiated) are used for attribution.Channel broadcasts that imply action: if a broadcast request is general (“Can someone…”, “Please review…”) →  HasTask=true, Assignee=unassigned. If it includes explicit targeting (“@X please…”) → assign to @XFor 1:1 chats, always attribute to the non-sender. Do not include unassigned/ambiguous asks unless the user explicitly requests them.If the user asks “what do we need to follow up on?” → show (1) tasks targeted to the user, then (2) a separate section “Needs owner / unclear assignee” for unassigned asks.If the user asks “my tasks” and the query intent is unclear → ask one clarifier: “Do you mean tasks assigned to you, or also tasks you’re involved in (followed/replied/initiated)?”If the user asks “Did anyone ask me to do something here?” and only unassigned asks exist → ask one clarifier: “Do you want items assigned to you only (explicit/implicit), or also general asks / tasks you’re following in this thread?”P1 (Phase 1): Personalization / expanded semanticsUnassigned/broadcast semantics: Different users interpret “tasks for me” differently. Define two modes: (1) Strict = only tasks explicitly/implicitly attributable to you; (2) Expanded = also include broadcast/unassigned asks you’re likely to own.Default to Strict for “tasks pending on me” (precision-first). Only surface broadcast/unassigned asks under a separate section (e.g., “Broadcast asks you may own”) when the user explicitly requests it, or when personalization indicates the user regularly treats broadcast items as theirs.Personalization (not required in P0): infer a user’s preference for Expanded vs Strict based on recent interaction patterns (e.g., consistently replying “I’ll take it” to broadcast asks, clicking Follow, initiating/owning threads). Use this only to include additional broadcast asks for that user; never change the stamped assignee on the message.Ranking rules for Copilot:“What do I need to act on?” → Filter HasTask = TRUE, then rank IsImportant = TRUE first, then by recency.“What should be on my radar?” → Show IsImportant = TRUE regardless of HasTask.“Catch me up” → Weight IsImportant = TRUE messages higher in summaries.Precision vs. Recall PhilosophyFavor precision over recall. False positives (“Copilot says I have a task, but I don’t”) erode trust faster than false negatives (“Copilot missed a task I can find myself”). Users will forgive occasional misses; they won’t forgive a noisy, unreliable task list.HasTask Precision: ≥ 85%; If Copilot says it’s a task, it should be one.Recall: ≥ 80%; Missing some tasks is acceptable; noise is not.IsImportant Precision ≥ 80%; False “important” flags cause alert fatigue.Attribution EXPLICIT ≥ 95%,	@mention parsing should be near-perfect.IMPLICIT ≥ 70% (	Name-in-text and reply-to are harder).Combined Quick-Reference TableMessageHasTaskIsImportantAttributionTask TypeDo you know how to download this data?TRUEFALSEImplicit (1:1)QuestionCan you call?TRUEFALSEImplicit (1:1)SchedulingDoes 2 PM work for you?TRUEFALSEImplicit (1:1)SchedulingCould you please review the Status Update post?TRUEFALSEExplicit (@)ReviewSome pressure to get it to design for LT preview tomorrowTRUETRUEImplicitActionFolks, I’m unwell.
